Overview

Wazuh is a free, open-source Security Information and Event Management (SIEM) platform built on Elasticsearch. In enterprise SOC operations, especially at scale (Safaricom with 100+ branch offices), a centralized SIEM is critical for threat detection, incident response, and compliance reporting.

This article covers:

  • Deploying Wazuh from scratch on Ubuntu/Docker
  • Configuring agents on Linux, Windows, and network devices
  • Ingesting logs from 100+ endpoints, firewalls, and databases
  • Writing custom detection rules
  • Mapping rules to MITRE ATT&CK framework
  • Tuning alerts to reduce false positives
  • Building executive dashboards

Architecture & Components

Wazuh consists of three core components:

Component Role Deployment
Wazuh Manager Centralized analysis engine; receives logs from agents, applies detection rules Central server (e.g., Ubuntu 22.04)
Wazuh Agents Lightweight collectors on endpoints (Windows, Linux, macOS) Distributed to endpoints
Kibana Dashboard Web UI for visualization, searching, alerting Central server (port 5601)

Wazuh Deployment from Scratch

For a Safaricom SOC deployment, you'd typically use Docker Compose for orchestration. Here's a minimal setup:

# docker-compose.yml
version: '3.8'
services:
  wazuh-manager:
    image: wazuh/wazuh:4.5.0
    environment:
      - INDEXER_URL=https://wazuh-indexer:9200
      - INDEXER_USERNAME=admin
      - INDEXER_PASSWORD=SecurePassword123
    ports:
      - "1514:1514"  # Agent communication (UDP)
      - "1515:1515"  # Agent communication (TCP)
      - "514:514"    # Syslog
    volumes:
      - wazuh-manager-data:/var/ossec/data
      - ./wazuh-config/:/wazuh-config-mount/:ro
    networks:
      - wazuh-network

  wazuh-indexer:
    image: wazuh/wazuh-indexer:4.5.0
    environment:
      - discovery.type=single-node
      - OPENDISTRO_INITIAL_ADMIN_PASSWORD=SecurePassword123
    ports:
      - "9200:9200"
    volumes:
      - wazuh-indexer-data:/usr/share/opensearch/data
    networks:
      - wazuh-network

  wazuh-dashboard:
    image: wazuh/wazuh-dashboard:4.5.0
    ports:
      - "443:5601"
    environment:
      - WAZUH_API_URL=https://wazuh-manager:55000
      - WAZUH_API_USERNAME=wazuh
      - WAZUH_API_PASSWORD=wazuh
    networks:
      - wazuh-network
    depends_on:
      - wazuh-manager

volumes:
  wazuh-manager-data:
  wazuh-indexer-data:

networks:
  wazuh-network:
Pro Tip: In production, you'd use a dedicated Ubuntu VM or Kubernetes cluster, not Docker on a single host. For Safaricom's scale, consider high availability (HA) setup with manager clustering.

Ingesting 100+ Data Sources

Wazuh agents are deployed on endpoints. Each agent sends logs back to the manager on port 1514 (UDP) or 1515 (TCP). Example agent configuration:

# Windows Agent (C:\\Program Files (x86)\\ossec-agent\\ossec.conf)
<agent_config>
  <localfile>
    <log_format>eventlog</log_format>
    <location>Security</location>
  </localfile>
  
  <localfile>
    <log_format>sysmon</log_format>
    <location>Sysmon/Operational</location>
  </localfile>
</agent_config>

Additionally, you can collect logs from network devices:

  • Firewalls: Palo Alto, Fortinet, Cisco ASA (via Syslog)
  • Databases: MySQL, PostgreSQL audit logs
  • Web Servers: Apache, Nginx access/error logs
  • Routers/Switches: Cisco, Juniper (via NetFlow/sFlow)

Wazuh ingests ~500 GB/day for a Safaricom deployment across 100+ branches.

Custom Detection Rules

Wazuh rules are XML-based. Example: detecting suspicious failed SSH logins (brute force):

<rule id="10100" level="5">
  <if_sid>5710</if_sid>
  <regex>authentication failure</regex>
  <description>SSH authentication failed</description>
  <group>authentication_failed</group>
</rule>

<rule id="10101" level="10">
  <if_matched_sid>10100</if_matched_sid>
  <same_source_ip />
  <frequency>5 in 30m</frequency>
  <description>Multiple SSH brute force attempts from same IP</description>
  <group>authentication_failed,brute_force</group>
  <mitre>
    <id>T1110</id>
  </mitre>
</rule>

This rule triggers at level 10 (alert) when 5 failed login attempts occur from the same IP within 30 minutes—a signature of brute force attacks.

MITRE ATT&CK Mapping

Map each detection rule to MITRE ATT&CK tactics and techniques. The brute force example above maps to:

  • Tactic: Credential Access (TA0006)
  • Technique: T1110 - Brute Force

In Wazuh dashboards, you'll see heatmaps showing which ATT&CK techniques are being exploited in your environment. This helps prioritize incident response and defense investment.

Alert Tuning & False Positive Reduction

Out-of-the-box Wazuh generates alerts for everything. For a 100-endpoint SOC, you'd receive thousands of daily alerts. 80% are typically false positives.

Tuning strategy:

  1. Whitelist known-good activities: Add Safaricom's internal admin IPs to exception lists
  2. Adjust severity levels: Lower alert level for expected scheduled tasks
  3. Add frequency thresholds: Only alert after N events in time window
  4. Correlate multiple rule triggers: Real incidents trigger 3-5 related rules simultaneously
# Whitelist example: Ignore alerts from internal IT admin
<rule id="10102" level="0">
  <if_sid>10101</if_sid>
  <source_ip>10.0.0.5|10.0.0.6</source_ip>
  <description>Internal admin SSH tests - ignored</description>
</rule>
Insight: Tuning takes weeks. Start with high-severity rules (level 10+), gradually lower thresholds as you build confidence. In month 1, expect alerts to be 90% false positives. By month 3, you'll be down to 20-30% false positives.

Building SOC Dashboards

Kibana dashboards visualize alerting and threats for the SOC team. Example widgets:

  • Alert Timeline: Alerts per hour (detect anomalies)
  • Top 10 Alerted Rules: Which detections are firing most
  • Top Source IPs: Which endpoints are generating alerts
  • MITRE ATT&CK Heatmap: Which attack techniques are active
  • Severity Distribution: Critical vs. High vs. Medium

Safaricom's SOC Lead uses a custom dashboard for daily standup showing:

  • Critical incidents requiring investigation
  • False positive rates (trending down = good tuning)
  • Top 3 branches by alert volume
  • Incident response SLA compliance (target: 30 min initial response)

Key Takeaways

Deploying a Wazuh SIEM at enterprise scale (Safaricom SOC operations):

  • Start simple: Deploy manager + agents, get logs flowing before adding rules
  • Tune aggressively: 80% of your effort is reducing false positives
  • Map to MITRE ATT&CK: Makes incident response repeatable and measurable
  • Correlate, don't alert on singles: Real incidents trigger multiple rules
  • Measure: Track alert volume, false positive rate, MTTR (mean time to respond)
  • Iterate: Every 2 weeks, review top 20 false positives and tune rules

With these practices, a 100-endpoint Safaricom SOC can reduce MTTR from 4 hours to under 30 minutes within 3 months.
